# BoringTun Router daemon — архитектура и план реализации

## Цель

Добавить в workspace отдельный Linux-сервис btrouted, который управляет несколькими независимыми WG/AWG-интерфейсами на базе существующей библиотеки BoringTun. Сервис читает один TOML-файл, создаёт TUN-интерфейсы, настраивает пиры напрямую через типизированный API BoringTun (без UAPI-сокетов и внешних wg/awg), управляет policy routing/nftables и собирает статистику.

Это отдельный продуктовый слой. Существующий boringtun-cli, библиотека boringtun и их совместимость не должны менять поведение.

## Архитектурные решения

### 1. Разделение ответственности

- **boringtun** — криптография, handshake, transport, timers, AWG framing.
- **btrouted** — TOML, жизненный цикл нескольких устройств, применение конфигурации, маршрутизация, статистика, логирование и CLI.
- **Linux kernel** — TUN, IP forwarding, таблицы маршрутизации и conntrack.
- **nftables** — классификация транзитных пакетов и установка packet mark. Маршрут выбирается ядром через ip rule fwmark и отдельную таблицу маршрутизации для каждого egress-интерфейса.

Один экземпляр BoringTun Device соответствует одному TUN-интерфейсу и одному UDP listen port. Внутри интерфейса может быть любое число пиров. Например, один WG-сервер с клиентами и два AWG-клиентских uplink — три Device в одном процессе.

### 2. Управление без UAPI

**Единый путь UAPI для внешних инструментов:** если UAPI включён, BoringTun создаёт ровно один Unix-сокет `/run/wireguard/<interface>.sock` для WG и всех вариантов AWG. Второй сокет и symlink в `/run/amneziawg` не создаются. Сам daemon использует типизированный API и не открывает UAPI endpoint.

Важно для развёртывания: upstream `amneziawg-tools` на Linux по умолчанию ищет userspace socket в каталоге `/amneziawg` под своим `RUNSTATEDIR`. Для совместимости в исходниках AWG tools нужно применить `patches/amneziawg-tools-uapi-path.patch`, а при сборке задать `RUNSTATEDIR=/run` (в `src/Makefile`). Тогда `awg` ищет тот же `/run/wireguard/<interface>.sock`. Без этого патча стандартный бинарник `awg` продолжит искать `/run/amneziawg/<interface>.sock` и не обнаружит сокет BoringTun.


Текущий Device умеет создавать TUN и обрабатывать UDP, но управление private key/peer/AllowedIPs сейчас завязано на внутренний UAPI parser. Не следует эмулировать UAPI через сокет или shell-команды. Нужен публичный типизированный control API в boringtun::device:

- DeviceConfig получает явные параметры интерфейса, в том числе listen port, mark внешних UDP-сокетов и настройки AWG.
- DeviceHandle получает операции configure/reconfigure: private key, peer add/update/remove, endpoint, PSK, keepalive, AllowedIPs.
- Конфигурация одного интерфейса валидируется целиком до применения; изменения ключа и peer state применяются атомарно настолько, насколько это возможно без потери активных сессий.
- UAPI handler остаётся только для обычного режима и использует те же внутренние операции; `DeviceConfig.enable_uapi=false` полностью отключает UAPI для конкретного Device: сокет/handler не создаётся, переданный `uapi_fd` игнорируется, event loop не обслуживает UAPI. `btrouted` обязан использовать только типизированный Control API.
- `DeviceConfig.listen_port` позволяет задать UDP-порт при создании `Device`; `None` сохраняет прежний выбор случайного порта.
- Статистика экспортируется из datapath через `DeviceHandle::snapshot()`, а не считывается парсингом UAPI. Snapshot содержит имя интерфейса, listen port, MTU, fwmark и по каждому peer: public key, index, endpoint, AllowedIPs, keepalive, возраст последнего handshake и TX/RX bytes. Счётчики пакетов пока не экспортируются: в текущем Noise datapath есть байтовые счётчики, но нет достоверных peer packet counters.

Это потребует небольшого рефакторинга: вынести существующие операции set_key, update_peer, set_obfuscation из UAPI-обработчика в общий внутренний слой, затем открыть безопасную публичную обёртку.

### 3. Версии WG/AWG

В конфиге версия протокола задаётся явно: wg, awg1, awg1_5, awg2, awg3, awg3_1. Слой конфигурации преобразует версию в конкретные поддерживаемые параметры BoringTun и проверяет допустимые поля. Нельзя трактовать версию как произвольную строку или молча игнорировать параметр, не поддерживаемый выбранной версией.

Нужно отдельно зафиксировать таблицу соответствия полей каждой версии протокола и проверить её тестами против эталонных конфигураций. Параметры имитации протокола/домена/браузера остаются startup-конфигурацией, поскольку для них нет UAPI-ключа.

### 4. Маршрутизация, изоляция интерфейсов и NAT

Связность между туннельными интерфейсами закрыта по умолчанию. Ни один интерфейс не может передавать трафик:
- другому туннельному интерфейсу;
- другому пиру того же интерфейса через маршрутизатор;
- физическому/иному интерфейсу хоста;
- любому другому направлению,
если для соответствующего потока нет явно совпавшего routing rule.

Это относится ко всем пирам всех WG/AWG-интерфейсов. Наличие адреса в одной подсети, AllowedIPs или системного маршрута само по себе не разрешает транзит. Для трафика между пирами, который не проходит через TUN/forward path демона, требуется отдельная изоляция на стороне соответствующего туннеля/узла.

Routing rule описывает направление и селекторы потока:
- `ingress` — интерфейс, с которого пришёл расшифрованный пакет;
- `egress` — интерфейс, через который пакет разрешено передать;
- `source` — необязательный список исходных сетей/адресов;
- `destination` — необязательный список сетей/адресов назначения;
- отсутствие обоих селекторов означает совпадение со всем IP-трафиком на указанном ingress;
- `priority` — порядок проверки; меньшее число проверяется раньше;
- `nat` — NAT для выбранного правила: `none` (значение по умолчанию) или `masquerade`.

`ingress` в первой версии должен иметь роль `server`, а `egress` — роль `client`. Один интерфейс не может одновременно быть ingress и egress одного правила. Ответный трафик не требует отдельного routing rule: он допускается только conntrack, если относится к соединению, ранее разрешённому прямым правилом, и возвращается на исходный ingress-интерфейс.

При совпадении нескольких правил применяется первое по возрастанию priority. Для одного ingress значения priority должны быть уникальными. Если заданы оба селектора, их списки должны иметь хотя бы одно общее семейство адресов; IPv4- и IPv6-CIDR обрабатываются раздельно.

Пример правила без IP-ограничений — весь трафик с интерфейса WG направляется через AWG:
```toml
[[routing.rules]]
priority = 100
ingress = "wg-server"
egress = "awg-client"
```

При необходимости селекторы ограничивают источники и назначения; каждый из них принимает одну строку CIDR или массив строк CIDR:
```toml
[[routing.rules]]
priority = 110
ingress = "wg-server"
source = ["10.150.150.0/24", "10.150.151.10/32"]
destination = ["192.168.10.0/24", "203.0.113.10/32"]
egress = "awg-client"
nat = "masquerade"
```

Для совместимости одиночные строковые значения CIDR также принимаются.

IPv6 для внутреннего трафика настраивается независимо на каждом туннеле через `ipv6_enabled` в соответствующей секции `[interfaces.<имя>]`. Значение по умолчанию — `false`: IPv6-пакеты блокируются при входе через этот TUN и при маршрутизации/локальной отправке в него. Для IPv6-транзита должны быть включены оба участвующих туннеля — ingress и egress. IPv6 policy routes создаются только для egress с `ipv6_enabled = true`; при отключении удаляются оставшиеся принадлежащие демону IPv6-маршруты и правила. Правила fwmark для внешнего UDP-транспорта BoringTun по-прежнему создаются для IPv4 и IPv6 и не зависят от этой настройки. Системные IPv6 sysctl этим параметром не меняются.

Для каждого egress создаётся отдельная routing table и fwmark/ip rule. nftables классифицирует только новые пакеты, совпавшие с routing rule, и сохраняет выбранный egress mark в conntrack. Для исходного направления mark восстанавливается до route lookup; для ответного направления mark очищается, чтобы ядро использовало обычный маршрут к ingress TUN. В forward chain разрешаются только совпавшие пары ingress/egress и обратные пакеты соответствующих conntrack-соединений. Пакеты, входящие или выходящие через любой управляемый TUN и не прошедшие эти разрешения, блокируются. Базовая политика цепочки остаётся accept, чтобы не менять транзитный трафик, не относящийся к интерфейсам btrouted.

NAT — свойство routing rule, а не интерфейса. NAT выполняется в postrouting только для потока, выбранного этим правилом, с проверкой ingress, egress, source/destination и conntrack mark. Правила NAT проверяются в том же порядке, что и routing rules; совпавшее правило с `nat = "none"` завершает обработку NAT и не позволяет последующим правилам изменить решение. Ответный NAT выполняется conntrack автоматически.

Обязательные меры против routing loop:
- каждый BoringTun UDP socket получает уникальный socket fwmark;
- mark транзитного inner traffic не совпадает с mark внешнего UDP;
- внешние UDP-пакеты BoringTun направляются через main table/физический uplink, а не обратно в TUN;
- endpoint IP/port и DNS bootstrap должны быть достижимы вне туннеля;
- маршруты и nft rules устанавливаются идемпотентно и только в принадлежащей демону таблице/цепочках.

nftables не должен переписывать чужие таблицы и default firewall policy. Демон добавляет свою таблицу, свои chains и набор управляемых интерфейсов. Forward chain ограничивает только пакеты, входящие или выходящие через TUN-интерфейсы btrouted; посторонний транзит хоста не должен затрагиваться. Для безопасного старта сначала создаётся полный nft batch, затем применяется атомарно; при остановке удаляются только ресурсы с собственным идентификатором. Не следует автоматически добавлять широкие ACCEPT-правила в чужие chains.

### 5. Обратный трафик, conntrack и forwarding

Новый поток разрешается только если пакет пришёл через настроенный ingress, совпал с source/destination селекторами routing rule и после route lookup выходит через указанный egress. Если совпадения нет, пакет не должен попасть ни в один другой TUN через main table или альтернативное правило: forward policy демона его блокирует.

На первом пакете выбранный egress mark записывается в conntrack. Пакеты исходного направления восстанавливают mark до route lookup. Пакеты ответного направления не используют egress mark — иначе они снова ушли бы в uplink; они направляются обычной таблицей к исходному ingress TUN и проходят только парное established/related разрешение. Conntrack не является глобальным разрешением: нужны корректные входной/выходной интерфейсы и сохранённая метка разрешённого потока.

`nat = "none"` сохраняет исходный IP. Удалённая сторона должна иметь обратный маршрут к исходной сети WG-клиента. `nat = "masquerade"` подменяет source IP адресом egress-интерфейса; conntrack восстанавливает адрес назначения на обратном пути. NAT не включается автоматически и не меняет политику фильтрации.

Управление `net.ipv4.ip_forward` и `net.ipv6.conf.all.forwarding` остаётся opt-in через `manage_ip_forwarding`, с сохранением исходных значений и восстановлением при остановке.

### 6. Статистика

Статистика должна быть нативной частью daemon API:
- TX/RX bytes для каждого peer (уже доступны через `DeviceHandle::snapshot()`); packet counters добавлять только после внедрения точного учёта в datapath;
- возраст последнего успешного handshake;
- endpoint, keepalive и AllowedIPs;
- состояние интерфейса и счётчики ошибок/переподключений;
- агрегаты по интерфейсу.

Счётчики bytes/packets добавляются в datapath BoringTun в точках успешной обработки/передачи пакета. Snapshot не должен блокировать обработку трафика. Для первой версии достаточно CLI `btrouted status` и структурированных логов. Отдельные Prometheus API и Web UI не входят в проект.

## План реализации согласованной модели фильтрации и маршрутизации

1. **Контракт конфигурации:** сохранить обязательные `ingress`/`egress`; сделать `source` и `destination` необязательными CIDR-селекторами (одиночная строка или массив). Если оба отсутствуют, правило совпадает со всем IP-трафиком ingress. Добавить `nat = "none" | "masquerade"`, по умолчанию NAT выключен. Валидировать интерфейсы/роли, совместимость семейств заданных source/destination и уникальность priority в пределах ingress.
2. **План маршрутизации:** генерировать детерминированные правила по ingress и priority, mark для выбранного egress и набор всех интерфейсов, которыми управляет демон.
3. **Ingress-классификация:** новые пакеты классифицировать только при совпадении routing rule; сохранять egress mark в conntrack. Не совпавший пакет не получает маршрутную метку.
4. **Forward isolation:** разрешать только прямое направление ingress → egress, совпавшее с routing rule, и обратное established/related направление по сохранённой conntrack mark. Любой другой пакет, входящий или выходящий через управляемый TUN, блокировать. Не менять forwarding для интерфейсов, не принадлежащих btrouted.
5. **Обратная маршрутизация:** очищать packet mark у reply-пакетов перед route lookup, чтобы ответ возвращался по main table на исходный ingress TUN, а не повторно уходил в uplink.
6. **NAT:** выполнять postrouting masquerade только для совпавшего routing rule; правило `nat = "none"` также завершает поиск NAT-решения. Conntrack обеспечивает обратную трансляцию.
7. **Тестирование:** unit-тесты конфигурации и nft script; namespace-тесты для default-drop, изоляции пиров одного/разных интерфейсов, разрешённого транзита, обратного трафика, NAT on/off, нескольких uplink и внешнего UDP BoringTun.
8. **Проверка регрессий:** сборка workspace, все unit-тесты и существующие короткие integration tests. Длительные тесты отложить до завершения последующих изменений фильтрации.

Критерий безопасности: отсутствие совпавшего routing rule означает отсутствие связности между управляемыми интерфейсами. Системный маршрут и AllowedIPs не являются самостоятельным разрешением на транзит.

## Реализация конфигурации

Первый слой парсера находится в crate `btrouted`:
- TOML десериализуется в типизированные структуры; неизвестные поля отклоняются;
- до создания системных ресурсов проверяются имена интерфейсов, уникальность UDP-портов и socket fwmark, ключи Base64 (ровно 32 байта), CIDR, endpoint, MTU, роли ingress/egress, source/destination address family, NAT mode и приоритеты правил;
- endpoint поддерживает IPv4, IPv6 в формате `[address]:port` и ASCII DNS-имена (включая IDN в punycode); TOML parsing проверяет имя и порт, но не выполняет DNS-запросы — разрешение имени относится к запуску/переподключению демона;
- проверяются дубликаты peer names/public keys и одинаковые AllowedIPs, назначенные разным пирам одного интерфейса;
- AWG H1-H4 проверяются на корректность uint32-диапазонов и взаимное пересечение; Jmin/Jmax должны задаваться парой;
- загрузка из файла и парсинг из строки доступны через `Config::load` и `Config::parse_toml`.

На первом этапе парсер принимает базовые AWG поля Jc/Jmin/Jmax, S1-S4, H1-H4, DisableCookies и RandomTrailers. Остальные AWG 3.x расширения будут добавляться после сверки полей с соответствующими эталонными версиями; неизвестные поля намеренно не игнорируются.

## Предлагаемая TOML-модель

- [daemon]: логирование, пути, интервал статистики, политика привилегий.
- [interfaces.<имя>]: именованная секция интерфейса с протоколом/версией, ролью, адресами TUN, MTU, listen port, private key и socket mark.
- [interfaces.<имя>.peers.<имя_пира>]: именованная секция пира с public key, PSK, endpoint, AllowedIPs и keepalive.
- [interfaces.<имя>.awg]: параметры конкретной версии AWG.
- [[routing.rules]]: обязательные ingress/egress, необязательные source/destination (один CIDR или массив CIDR), priority и NAT mode (`none`/`masquerade`).
- [routing]: nft table name, mark base и политика управления forwarding.

Private keys и PSK в TOML удобны для первого релиза, но файл должен иметь права 0600. В будущем добавить *_file/secret provider, не печатать секреты в логах и поддержать атомарную ротацию.

## Этапы разработки

### Этап 0 — контракт и тестируемая конфигурация
- утвердить схему TOML и семантику правил;
- сделать parser + строгую валидацию без root;
- добавить пример и документацию;
- golden tests на маршруты, приоритеты, пересечения CIDR, дубликаты marks/имён/портов.

### Этап 1 — публичный BoringTun control API
- вынести управление интерфейсом/пирами из UAPI parser;
- добавить startup listen port и socket fwmark в DeviceConfig;
- добавить read-only peer/interface stats;
- сохранить UAPI поведение и все существующие тесты.

### Этап 2 — минимальный daemon
- отдельный workspace crate btrouted;
- запуск нескольких WG/AWG Device из TOML;
- конфигурация без UAPI;
- systemd unit, foreground mode, корректное завершение и очистка TUN.

### Этап 3 — маршрутизация Linux и изоляция
- nft batch с fail-closed фильтрацией для всех управляемых TUN-интерфейсов;
- классификация новых потоков по ingress и необязательным source/destination селекторам (включая правило без IP-селекторов) и выбор egress через packet mark;
- conntrack mark для сохранения направления и безопасной обратной маршрутизации;
- NAT none/masquerade на уровне routing rule в postrouting;
- запрет неописанного транзита между интерфейсами, включая пиры одного интерфейса;
- управление ip rule и routing tables, защита от routing loop для UDP endpoints;
- rollback при частичной ошибке применения;
- network namespace integration tests для разрешённого/запрещённого транзита, NAT и обратных потоков.

### Этап 4 — статистика и эксплуатация
- peer/interface counters;
- status CLI и JSON;
- reload по SIGHUP с validate-then-apply;
- внутренний read-only snapshot API для будущих интеграций, без отдельного HTTP API.

### Этап 5 — отказоустойчивость и расширения
- health checks и handshake timeout;
- приоритетные uplinks/failover;
- статический SNAT, расширенные per-source/per-peer selectors, дополнительные IPv6-политики;
- rate limits, audit log, конфигурация секретов.

### Этап 6 — Telegram Bot API (отдалённый, необязательный приоритет)
- подключать только после стабилизации демона и внутреннего Control Manager;
- разрешённые операции: создание, изменение и удаление пиров, управление туннелями, получение статистики и состояния;
- бот обращается к Control Manager через ограниченный локальный IPC/API и не выполняет системные команды самостоятельно;
- авторизация по allowlist Telegram user ID, журналирование административных действий и защита секретов;
- Web UI и Prometheus API не реализуются.

## Критерии готовности первой рабочей версии

1. Один процесс поднимает WG server + два AWG uplink с разными версиями.
2. Пиры настраиваются только из TOML и внутреннего API, UAPI socket не создаётся.
3. Весь трафик от WG server идёт через основной AWG uplink, кроме двух заданных CIDR через второй.
4. Внешние UDP-пакеты обоих AWG endpoints не попадают в VPN-маршрут.
5. Счётчики по каждому peer корректно растут в обе стороны.
6. Невалидный TOML или ошибка nft/ip не оставляют систему в частично настроенном состоянии.
7. Тесты маршрутизации выполняются в изолированных network namespaces и не требуют изменения firewall хоста.
8. Без routing rule связность между управляемыми интерфейсами отсутствует; NAT применяется только по выбранному правилу и выключен по умолчанию.
