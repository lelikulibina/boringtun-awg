# BoringTun Router daemon — архитектура и план реализации

## Цель

Добавить в workspace отдельный Linux-сервис btrouted, который управляет несколькими независимыми WG/AWG-интерфейсами на базе существующей библиотеки BoringTun. Сервис читает один TOML-файл, создаёт TUN-интерфейсы, настраивает пиры напрямую через типизированный API BoringTun (без UAPI-сокетов и внешних wg/awg), управляет policy routing/nftables и собирает статистику.

Это отдельный продуктовый слой. Существующий boringtun-cli, библиотека boringtun и их совместимость не должны менять поведение.

## Архитектурные решения

### 1. Разделение ответственности

- **boringtun** — криптография, handshake, transport, timers, AWG framing.
- **btrouted** — TOML, жизненный цикл нескольких устройств, применение конфигурации, маршрутизация, статистика, логирование и CLI.
- **Linux kernel** — TUN, IP forwarding, таблицы маршрутизации и conntrack.
- **nftables** — классификация транзитных пакетов и установка packet mark. Маршрут выбирается ядром через ip rule fwmark и отдельную таблицу маршрутизации для каждого egress-интерфейса.

Один экземпляр BoringTun Device соответствует одному TUN-интерфейсу и одному UDP listen port. Внутри интерфейса может быть любое число пиров. Например, один WG-сервер с клиентами и два AWG-клиентских uplink — три Device в одном процессе.

### 2. Управление без UAPI

Текущий Device умеет создавать TUN и обрабатывать UDP, но управление private key/peer/AllowedIPs сейчас завязано на внутренний UAPI parser. Не следует эмулировать UAPI через сокет или shell-команды. Нужен публичный типизированный control API в boringtun::device:

- DeviceConfig получает явные параметры интерфейса, в том числе listen port, mark внешних UDP-сокетов и настройки AWG.
- DeviceHandle получает операции configure/reconfigure: private key, peer add/update/remove, endpoint, PSK, keepalive, AllowedIPs.
- Конфигурация одного интерфейса валидируется целиком до применения; изменения ключа и peer state применяются атомарно настолько, насколько это возможно без потери активных сессий.
- UAPI handler остаётся совместимым и использует те же внутренние операции, но демон его не включает.
- Статистика экспортируется из datapath через read-only snapshot API, а не считывается парсингом UAPI.

Это потребует небольшого рефакторинга: вынести существующие операции set_key, update_peer, set_obfuscation из UAPI-обработчика в общий внутренний слой, затем открыть безопасную публичную обёртку.

### 3. Версии WG/AWG

В конфиге версия протокола задаётся явно: wg, awg1, awg1_5, awg2, awg3, awg3_1. Слой конфигурации преобразует версию в конкретные поддерживаемые параметры BoringTun и проверяет допустимые поля. Нельзя трактовать версию как произвольную строку или молча игнорировать параметр, не поддерживаемый выбранной версией.

Нужно отдельно зафиксировать таблицу соответствия полей каждой версии протокола и проверить её тестами против эталонных конфигураций. Параметры имитации протокола/домена/браузера остаются startup-конфигурацией, поскольку для них нет UAPI-ключа.

### 4. Маршрутизация и пример пользователя

Для каждого egress-интерфейса создаётся отдельная routing table с default route через соответствующий TUN. Для каждого egress назначается уникальный packet mark и ip rule fwmark. nftables классифицирует forwarded-пакеты по входному интерфейсу и адресу назначения, устанавливает mark; ядро выполняет lookup в нужной таблице.

Правила имеют явный priority: меньшее значение проверяется раньше. Поэтому исключения /16 и /24 должны стоять выше default /0. Для приведённого сценария:

1. Пакет пришёл с wg-server, destination 195.142.0.0/16 или 79.100.22.0/24 → awg-secondary.
2. Остальной IPv4/IPv6 трафик с wg-server → awg-primary.

AllowedIPs у WireGuard peer и правила транзитной маршрутизации — разные понятия. Первые отвечают за криптографическое владение адресами внутри конкретного Device; вторые определяют, в какой uplink передавать уже расшифрованный IP-пакет.

Обязательные меры против routing loop:
- каждый BoringTun UDP socket получает уникальный socket fwmark;
- маркировка транзитного inner traffic не должна совпадать с mark внешнего UDP;
- внешние UDP-пакеты BoringTun направляются через main table/физический uplink, а не обратно в TUN;
- endpoint IP/port и DNS bootstrap должны быть достижимы вне туннеля;
- маршруты и nft rules устанавливаются идемпотентно и только в принадлежащей демону таблице/цепочках.

nftables не должен переписывать чужие таблицы и default firewall policy. Демон добавляет свою таблицу, свои chains и правила. Для безопасного старта сначала создаётся полный nft batch, затем применяется атомарно; при остановке удаляются только ресурсы с собственным идентификатором. Не следует автоматически добавлять широкие ACCEPT-правила в чужие chains.

### 5. Обратный трафик, NAT и forwarding

По умолчанию предполагается маршрутизируемая схема без NAT: удалённые сети должны знать обратный маршрут через VPN-сервер. Опциональный SNAT/MASQUERADE может быть добавлен позже на уровне отдельного routing policy. Нужно явно документировать net.ipv4.ip_forward и net.ipv6.conf.all.forwarding; включение sysctl должно быть opt-in и иметь обратимое поведение при остановке.

Conntrack/асимметричная маршрутизация требуют тестов отдельно: одинаковый flow должен сохранять выбранный uplink для обратного направления. В первой версии не обещать автоматическое failover без отдельной модели состояния.

### 6. Статистика

Статистика должна быть нативной частью daemon API:
- bytes/packets RX и TX для каждого peer;
- последнее успешное handshake и возраст handshake;
- endpoint, keepalive и AllowedIPs;
- состояние интерфейса и счётчики ошибок/переподключений;
- агрегаты по интерфейсу.

Счётчики bytes/packets добавляются в datapath BoringTun в точках успешной обработки/передачи пакета. Snapshot не должен блокировать обработку трафика. Для первой версии достаточно CLI `btrouted status` и структурированных логов. Отдельные Prometheus API и Web UI не входят в проект.

## Предлагаемая TOML-модель

- [daemon]: логирование, пути, интервал статистики, политика привилегий.
- [[interfaces]]: имя, протокол/версия, роль, адреса TUN, MTU, listen port, private key, socket mark.
- [[interfaces.peers]]: public key, PSK, endpoint, AllowedIPs, keepalive.
- [interfaces.awg]: параметры конкретной версии AWG.
- [[routing.rules]]: ingress, destination CIDR, egress, priority.
- [routing]: nft table name, базовые настройки и политика управления forwarding/NAT.

Private keys и PSK в TOML удобны для первого релиза, но файл должен иметь права 0600. В будущем добавить *_file/secret provider, не печатать секреты в логах и поддержать атомарную ротацию.

## Этапы разработки

### Этап 0 — контракт и тестируемая конфигурация
- утвердить схему TOML и семантику правил;
- сделать parser + строгую валидацию без root;
- добавить пример и документацию;
- golden tests на маршруты, приоритеты, пересечения CIDR, дубликаты marks/имён/портов.

### Этап 1 — публичный BoringTun control API
- вынести управление интерфейсом/пирами из UAPI parser;
- добавить startup listen port и socket fwmark в DeviceConfig;
- добавить read-only peer/interface stats;
- сохранить UAPI поведение и все существующие тесты.

### Этап 2 — минимальный daemon
- отдельный workspace crate btrouted;
- запуск нескольких WG/AWG Device из TOML;
- конфигурация без UAPI;
- systemd unit, foreground mode, корректное завершение и очистка TUN.

### Этап 3 — маршрутизация Linux
- генерация nft batch для классификации forwarded traffic;
- управление ip rule и routing tables;
- защита от routing loop для UDP endpoints;
- rollback при частичной ошибке применения;
- network namespace integration tests.

### Этап 4 — статистика и эксплуатация
- peer/interface counters;
- status CLI и JSON;
- reload по SIGHUP с validate-then-apply;
- внутренний read-only snapshot API для будущих интеграций, без отдельного HTTP API.

### Этап 5 — отказоустойчивость и расширения
- health checks и handshake timeout;
- приоритетные uplinks/failover;
- per-source/per-peer policy, IPv6, selective NAT;
- rate limits, audit log, конфигурация секретов.

### Этап 6 — Telegram Bot API (отдалённый, необязательный приоритет)
- подключать только после стабилизации демона и внутреннего Control Manager;
- разрешённые операции: создание, изменение и удаление пиров, управление туннелями, получение статистики и состояния;
- бот обращается к Control Manager через ограниченный локальный IPC/API и не выполняет системные команды самостоятельно;
- авторизация по allowlist Telegram user ID, журналирование административных действий и защита секретов;
- Web UI и Prometheus API не реализуются.

## Критерии готовности первой рабочей версии

1. Один процесс поднимает WG server + два AWG uplink с разными версиями.
2. Пиры настраиваются только из TOML и внутреннего API, UAPI socket не создаётся.
3. Весь трафик от WG server идёт через основной AWG uplink, кроме двух заданных CIDR через второй.
4. Внешние UDP-пакеты обоих AWG endpoints не попадают в VPN-маршрут.
5. Счётчики по каждому peer корректно растут в обе стороны.
6. Невалидный TOML или ошибка nft/ip не оставляют систему в частично настроенном состоянии.
7. Тесты маршрутизации выполняются в изолированных network namespaces и не требуют изменения firewall хоста.
